# Plugin Architecture

This document describes the plugin architecture behind a hotel payment & billing platform I designed and built.

The platform owns the infrastructure — authentication, sessions, access control, audit logging, key management, database access, and communication. Business logic lives in plugins: signed DLLs that are loaded only after their signature has been verified, and routed to the correct handler by a simple service ID. Each business domain ships as a matched client/server pair.

Plugins never touch infrastructure code directly. As a result, adding a new domain is a matter of dropping in a new DLL, and updating business logic does not require redeploying the platform runtime.

It also means the platform underneath can evolve over time — new protocols, new security mechanisms, new deployment models — without rewriting the business logic running on top of it.


# From GitHub Actions to a Single PS1: Why We Left Managed CI/CD Behind

In my last post, I covered our GitHub Actions pipeline. This one's about why we dropped it — and what replaced it.

Managed CI/CD is powerful, but it's also infrastructure: YAML to maintain, runners to pay for, a queue to wait on, a dashboard to check. For a small team shipping to many hotel sites, each with its own product configuration, that overhead outweighed the benefit. We wanted something we could run, watch, and trust end-to-end — so we absorbed deployment into the platform itself.

The entire pipeline is one script. Running publish.ps1 from Visual Studio builds Server and Client, obfuscates, signs, zips, uploads a GitHub Release, and pushes a commit to our distribution repo — with the commit message doubling as the release note (DistName|release note). No separate release step, no trigger, no status page. When the terminal says "All Completed," it's deployed.

Director — the tool that handles the rest — is itself a plugin on the same platform described above, not a separate system bolted on the side. It doesn't poll; when a developer opens the version history screen, it pulls commits from the distribution repo on demand and parses them into version records (yy.MMdd.HHmmss_commitHash). For server deployments, a developer picks a site and clicks Install or Update — Director builds a package scoped to that site's exact configuration and generates a PS1 for the customer to run. For clients, there's no manual step at all: on connect, the server compares the client's version against the latest and pushes only the changed files, applied automatically on next launch.

The deployment history is just the commit log. No audit tables, no event log, no separate dashboard — Director reads the same commits the pipeline wrote and shows which sites are on which version.

We gave up automatic rollback, blue-green deploys, and a CI/CD dashboard. What we got instead: a pipeline a developer never leaves Visual Studio for, a history that writes itself, and a distribution system with no cost beyond the GitHub repo it already uses. And since Director is just another plugin, it's also living proof that the platform's own architecture holds up under its own tooling.
